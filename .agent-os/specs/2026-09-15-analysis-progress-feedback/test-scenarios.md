# 분석 진행 상태 피드백 테스트 시나리오

## 테스트 원칙

- 실제 Gemini·외부 JD 서비스 대신 서비스 mock, hook adapter 또는 deferred Promise를 사용한다.
- 각 테스트는 요청 시작·해결·실패 시점을 직접 제어해 임의의 sleep에 의존하지 않는다.
- 진행 상태 모듈의 seam과 사용자에게 보이는 진행 영역을 함께 검증한다.

## 시나리오

### TC-01 분석 시작 직후

- 조건: 입력 검증을 통과하고 분석 시작을 누른다.
- 검증: 결과 화면과 전체 진행 영역이 즉시 나타나며 `분석 진행 중`, `aria-busy=true`가 표시된다.

### TC-02 이력서 진단 대기

- 조건: 이력서 진단 Promise를 해결하지 않은 상태로 둔다.
- 검증: 이력서 항목만 진행 중이고 후속 항목은 대기 또는 준비 상태이며, 전체 완료 문구가 나타나지 않는다.

### TC-03 선택 항목에 따른 목록

- 조건: JD 적합도와 ATS만 선택한다.
- 검증: 문장 첨삭과 키워드 항목은 노출되지 않고, JD 적합도·ATS·결과 저장 그룹만 추적된다.

### TC-04 JD 적합도·키워드 공유 요청

- 조건: JD 적합도와 키워드 분석을 모두 선택한다.
- 검증: match 요청은 한 번만 호출되고 두 화면 결과가 같은 실행 그룹의 완료 상태를 공유한다.

### TC-05 병렬 요청의 완료 순서

- 조건: ATS가 먼저 성공하고 문장 첨삭과 이력 저장은 아직 진행 중이다.
- 검증: ATS만 완료로 표시되고 전체 상태는 계속 진행 중이다. 마지막 요청이 끝난 뒤에만 완료로 바뀐다.

### TC-06 일부 분석 실패

- 조건: JD 적합도는 성공하고 문장 첨삭은 실패한다.
- 검증: JD 결과는 유지되고 문장 첨삭에는 실패 상태·안내가 표시되며 전체 상태는 부분 실패다.

### TC-07 이력서 진단 실패

- 조건: 이력서 진단이 실패한다.
- 검증: 후속 분석이 성공 또는 완료로 표시되지 않고, 실패 이유와 재시작 안내가 표시된다.

### TC-08 중복 클릭과 오래된 응답

- 조건: 진행 중 시작 동작을 두 번 호출하거나, 첫 실행의 응답을 새 실행 시작 뒤에 해결한다.
- 검증: 실제 분석 요청은 한 실행당 한 번만 생성되고, 첫 실행의 응답이 두 번째 실행의 상태를 변경하지 않는다.

### TC-09 초기화와 회귀

- 조건: 진행 중 새 분석으로 이동하거나 분석을 종료한다.
- 검증: 이전 진행 목록이 초기화되고 새 입력 화면은 idle 상태다. 기존 결과 내보내기와 standalone JD fetch/interview 흐름은 기존 테스트를 통과한다.

### TC-10 접근성·모션

- 조건: 진행 중·성공·실패 상태를 키보드와 스크린 리더 관점에서 확인하고 `prefers-reduced-motion: reduce`를 적용한다.
- 검증: 상태 텍스트가 전달되고 `aria-busy`가 정확히 전환되며, 모션 없이도 진행·완료·실패 의미가 유지된다.

## 검증 명령

```text
cd frontend && npm run lint
cd frontend && npm test
cd frontend && npm run build
docker compose -f compose.local.yaml up -d --build
```

프론트 코드 변경 후에는 컨테이너 상태와 관련 health endpoint도 확인한다.
