# 분석 진행 상태 피드백 요구사항

```yaml
status: active
product_scope: Service MVP UX correction
risk: Low
```

## 목표

사용자가 `분석 시작하기`를 누른 뒤 현재 분석이 실제로 진행 중인지, 어떤 단계가 끝났고 어떤 단계가 남았는지 알 수 있게 한다. 현재 화면은 실제 요청이 끝나기 전에 결과 화면으로 전환되고 각 결과 카드의 로딩 메시지만 개별로 표시하므로, 전체 분석의 진행 여부와 완료 시점을 신뢰하기 어렵다.

## 범위

### 포함

- 메인 분석 흐름의 전체 진행 상태 표시
- 이력서 진단, 선택한 분석 항목, 분석 결과 저장의 실제 요청 상태 연결
- 선택된 항목별 대기 중·진행 중·완료·실패 상태
- 여러 분석 요청이 병렬로 실행될 때의 전체 상태 계산
- 부분 실패를 성공으로 오인하지 않는 안내
- 중복 클릭과 이전 분석의 늦은 응답이 현재 분석 상태를 오염시키지 않는 처리
- 키보드·스크린 리더를 포함한 접근성 상태 전달

### 제외

- 백엔드 progress API, SSE/WebSocket, Redis, 비동기 worker 도입
- 서버가 계산하지 않은 실제 퍼센트·잔여 시간·완료 예정 시각 표시
- AI 호출량·비용 제한과 quota 정책
- 별도 모의면접 화면과 JD 링크 자동 수집 자체의 로딩 UI 변경
- 분석 중 취소·재개·백그라운드 재접속

## 요구사항

### REQ-01 분석 시작 상태

유효한 입력으로 분석을 시작하면 결과 화면에 진입하는 즉시 전체 진행 상태가 `분석 진행 중`으로 표시되어야 한다. 사용자는 버튼 문구만으로 진행 여부를 추측하지 않아야 한다.

### REQ-02 실제 요청 경계 기반 상태

진행 상태는 임의의 시간 지연이나 가짜 퍼센트가 아니라 현재 프론트가 호출한 실제 비동기 요청의 시작·종료 결과를 기반으로 전환되어야 한다.

### REQ-03 선택 항목 반영

선택한 분석 항목만 진행 목록에 포함한다. `JD 적합도`와 `키워드 분석`은 현재 동일한 JD match 요청을 공유하므로 중복 요청을 만들지 않고 하나의 실행 그룹으로 추적한다.

### REQ-04 전체 완료 판정

선택된 모든 분석 그룹과 분석 이력 저장 요청이 종료되기 전에는 전체 상태를 `완료`로 표시하지 않는다. 하나라도 진행 중이면 전체 상태는 계속 `분석 진행 중`이어야 한다.

### REQ-05 실패와 부분 결과

하나의 분석 그룹이 실패하면 해당 그룹의 오류를 명확히 표시하고 전체 상태를 성공으로 표시하지 않는다. 다른 그룹의 성공 결과는 숨기지 않되, 전체 상태는 `일부 분석 실패` 또는 `분석 실패`로 구분한다.

### REQ-06 분석 실행 격리

새 분석을 시작하면 이전 실행의 상태와 결과를 초기화한다. 실행 식별자를 사용해 이전 요청의 늦은 응답이 새 분석의 진행 상태를 덮어쓰지 않게 한다. 분석 중 중복 시작은 차단한다.

### REQ-07 접근성

진행 중·완료·실패 상태와 현재 단계는 색상이나 애니메이션만으로 전달하지 않는다. 상태 텍스트, 적절한 live region, `aria-busy`를 사용한다. 움직이는 로딩 표시에는 `prefers-reduced-motion` 대응을 제공한다.

### REQ-08 기존 계약 보존

기존 분석 endpoint, 서비스 계층, 결과 데이터 계약을 변경하지 않는다. 프론트 컴포넌트는 직접 네트워크 호출을 하지 않고 기존 서비스·hook 경계를 재사용한다.

## 설계 원칙

진행 상태를 여러 화면 컴포넌트가 각자 계산하지 않고, 하나의 얕은 호출 인터페이스를 가진 진행 상태 모듈(예: `useAnalysisProgress`)에서 관리한다. 이 모듈의 외부 인터페이스는 실행 시작, 요청 상태 갱신, 실행 종료 상태 조회로 제한하고, 요청 그룹·실행 식별자·부분 실패 계산은 내부에 숨긴다. 화면과 테스트는 이 seam을 통해 동일한 상태를 관찰한다.
