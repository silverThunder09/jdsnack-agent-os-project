# 분석 진행 상태 피드백 UI 계약

## 적용 화면

- 적용: 인증된 사용자의 메인 분석 흐름인 `AnalysisInputView` → `AnalysisResultView`
- 제외: standalone JD 링크 수집 상태와 `InterviewWorkspace`의 독립 요청 상태는 기존 표시를 유지한다.

## 배치

`AnalysisResultView`의 헤더 아래, 요약 카드와 결과 패널보다 먼저 전체 진행 영역을 표시한다. 분석 실행 중에는 결과 패널이 개별적으로 로딩·성공·실패 상태를 계속 보여줄 수 있지만, 전체 진행 영역이 최상위 상태의 정본이다.

## 전체 상태

| 상태 | 사용자 문구 | 동작 |
|---|---|---|
| `idle` | 표시하지 않음 | 입력 화면 또는 새 실행 대기 |
| `running/preparing` | `이력서와 입력을 확인하고 있습니다` | 이력서 진단 진행 중, 완료 아님 |
| `running/analyzing` | `선택한 분석을 진행하고 있습니다` | 선택 task별 상태 표시 |
| `running/saving` | `분석 결과를 저장하고 있습니다` | 결과는 보일 수 있지만 전체 완료 아님 |
| `succeeded` | `분석이 완료되었습니다` | `aria-busy=false`, 정상 결과 안내 |
| `partial-failure` | `일부 분석을 완료하지 못했습니다` | 성공 결과 유지, 실패 task 안내 |
| `failed` | `분석을 완료하지 못했습니다` | 실패 원인과 새 분석 안내 |

## task 표시

- `pending`: `대기 중`
- `running`: `진행 중`과 indeterminate loading indicator
- `succeeded`: `완료`와 체크 의미
- `failed`: `실패`와 사용자 행동 안내
- `skipped`: `실행되지 않음`과 진단 실패 등 이유

표시 순서는 이력서 진단 → 선택 분석 그룹 → 결과 저장이다. 선택되지 않은 task는 렌더링하지 않는다. JD 적합도와 키워드가 함께 선택된 경우에는 각각 결과 영역은 유지하되 진행 목록에서는 `JD 적합도·키워드 분석` 하나로 묶어 중복 실행으로 오해하지 않게 한다.

## 입력과 버튼

- 분석 실행 중 중복 시작을 막는다.
- 실행 중 `새 분석`은 비활성화하거나 실행 중임을 명확히 안내한다. 완료·부분 실패·실패 상태에서는 다시 활성화한다.
- 실행 중에도 이미 성공한 결과는 읽을 수 있지만, 전체 상태가 완료되기 전에는 완료 문구를 표시하지 않는다.
- 임의의 숫자 퍼센트, ETA, 서버가 확인하지 않은 `AI가 몇 % 진행됨` 같은 표현은 사용하지 않는다.

## 접근성

- 진행 영역은 `role="status"`와 `aria-live="polite"`를 사용한다.
- 전체 실행 중에는 진행 영역 또는 결과 영역에 `aria-busy="true"`를 적용하고 terminal 상태에서 `false`로 전환한다.
- 실패는 색상만으로 표현하지 않고 상태 텍스트와 안내 문장을 함께 제공한다.
- `prefers-reduced-motion: reduce`에서는 로딩 애니메이션을 줄이거나 제거해도 상태 텍스트와 구조는 유지한다.
- 새 진행 영역이 나타날 때 포커스를 강제로 빼앗지 않는다. 상태 변경은 live region으로 알리고 기존 키보드 위치를 보존한다.

## 회귀 경계

기존 `StatusMessage`, 개별 분석 결과 카드, 결과 내보내기, 인쇄, standalone JD fetch, 모의면접의 상태 표현을 진행 coordinator가 불필요하게 재작성하지 않는다. 공통 진행 표시를 추가하되 각 결과 hook의 기존 loading/success/error 계약은 유지한다.
